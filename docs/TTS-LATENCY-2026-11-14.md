# 连续朗读延迟优化验证

2026-11-14，在本地中文小说样本中选取开头五个有效正文句片段，使用 MiMo 配置真实调用。原文不修改；没有进行整本合成，小说正文与个人配置不纳入仓库。

| 片段 | 字符数（含空白） | 完整音频返回耗时 | 音频时长 | 解码耗时 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 66 | 4736 ms | 15040 ms | 66 ms |
| 2 | 6 | 744 ms | 960 ms | 2 ms |
| 3 | 125 | 7297 ms | 23840 ms | 31 ms |
| 4 | 4 | 573 ms | 960 ms | 2 ms |
| 5 | 25 | 2402 ms | 5760 ms | 8 ms |

旧逻辑在第二句开始播放时才请求第三句：0.96 秒短句无法覆盖 7.297 秒的合成等待，推算会有约 6.34 秒的网络欠载等待，另有播放器加载开销。第四句后也存在同类情况。

升级采用两路并发，最多六句在途/缓存，首播先准备两句。合成完成立即创建并预加载音频，真正切句时直接播放已经准备的对象。播放完的原始数据与音频对象立即回收；停止或跳转按播放代次废弃旧结果并取消请求。暂停时停止扩充预取队列，已有请求完成后保留给继续播放。未来句合成失败时先读完当前句，再在到达失败位置时报告错误。

采用同一组实测合成耗时与音频时长，以 0.1 倍时间缩放，在 Electron 浏览器中分别运行升级前后的播放器，使用可解码的静音 WAV 隔离模型内部停顿。记录前句结束到后句 `play()` 确认播放之间的等待：

| 切换 | 旧版 | 新版 |
| --- | ---: | ---: |
| 1 → 2 | 50 ms | 1 ms |
| 2 → 3 | 653 ms | 1 ms |
| 3 → 4 | 49 ms | 0 ms |
| 4 → 5 | 145 ms | 0 ms |

这是控制条件下的缩时回放结果，不能当作真实云端长时间播放的保证。真实返回音频中已有的句尾静音会保留；没有强行裁掉呼吸或自然停顿。持续低速网络、服务限流或大幅提高倍速，仍可能耗尽缓冲。首播两句缓冲也可能增加首次出声等待。

本轮选择优化非流式播放，避免同时引入 SSE 分帧、PCM 解码与采样率处理的变量。并未把非流式接口描述为流式实现。

验证结果：11 项 TTS 单元测试通过；Vue / TypeScript 类型检查通过；全仓 ESLint 为 0 错误（保留非空断言等警告）；源码构建与新版 Windows 产物的桌面交互测试均通过。发布产物沿用原有关闭 Node 调试参数的配置，自动化验证使用临时开启调试 fuse 的副本，业务代码与资源相同，测试后移除副本。

新版程序：`dist/tts-upgrade/win-unpacked/marktext.exe`。启动脚本优先打开新版，旧版目录保留作回退。应用正在运行时需先退出旧版，避免单实例机制把新文件转交给旧进程。
